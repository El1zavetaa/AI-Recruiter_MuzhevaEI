AI-Recruiter: мультиагентная система семантического ранжирования и скоринга кандидатов

Итоговый отчёт по проекту (Задача №3). Прототип, дата отчёта: сентябрь 2026.

1. Постановка задачи

Крупные ИТ-компании ежедневно получают тысячи откликов на вакансии, и рекрутеры вручную скринингуют резюме. Классический поиск по ключевым словам не понимает контекста и синонимов: формулировка «разрабатывал архитектуру распределённых систем на Go» может быть занижена поиском по жёсткому тегу «Golang» / «Backend Engineer». При этом рекрутеру важен не просто отсортированный список, а текстовое обоснование — почему конкретный кандидат подходит под сложные требования вакансии.

Цель проекта: разработать прототип интеллектуального программного комплекса, который семантически сопоставляет неструктурированные тексты резюме с требованиями вакансии, строит точный ранжированный список кандидатов и генерирует текстовые аналитические отчёты с обоснованием соответствия.

Ключевые задачи:

  • библиотека ИИ-инструментов (Tools): извлечение эмбеддингов, индексация, поиск top-K по косинусному сходству;
  • единый JSON-контракт между модулями (вакансии, чанки резюме, скоры близости);
  • мультиагентное ядро: минимум два агента — Технический Скринер и HR-Аналитик;
  • модуль генерации отчёта: финальный взвешенный скор + карточка кандидата (Плюсы / Риски / Вердикт).

Пайплайн состоит из модулей, повторяющих архитектуру из задания:

Принципиальное архитектурное решение: инструменты вычисляют факты, LLM только формулирует текст на их основе. Технический Скринер и HR-Аналитик сначала вызывают детерминированные функции (check_mandatory_skills, extract_experience_years, find_keyword_evidence), и лишь затем передают вычисленные факты в LLM для связного изложения. Это резко снижает риск галлюцинаций — LLM физически не может "придумать" навык или цифру стажа, которых нет в фактах, потому что не видит сырого резюме напрямую, только структурированную сводку.

Офлайн-режим (RuleBasedLLM) — осознанное решение: проект должен гарантированно воспроизводиться сначала без сети и API-ключей. Контракт LLMClient.complete(system_prompt, user_prompt) → str одинаков для обеих реализаций, поэтому переключение на настоящую LLM (Llama-3 через Ollama) — это одна переменная окружения (LLM_BACKEND=openai), без изменений в agents.py и orchestrator.py.

Финальный скор

Взвешенная агрегация трёх сигналов (веса заданы в orchestrator.py, подобраны экспертно):

final_score = 0.30 × similarity_score   (семантическая близость к вакансии)
            + 0.45 × technical_score    (скор Технического Скринера)
            + 0.25 × hr_score            (скор HR-Аналитика)

Вердикт:  ≥75 → «Рекомендован к приглашению»
          50–74 → «В резерв»
          <50 → «Отказ»

3. Результаты экспериментов и метрики

Для объективной (не только качественной) оценки качества ранжирования была сгенерирована демонстрационная база из 12 синтетических резюме (generate_demo_data.py, seed=42, воспроизводимо). Каждому резюме при генерации присваивается скрытая "истинная метка" — трек (mlops / backend_go / data_scientist / irrelevant), которая не участвует ни в эмбеддингах, ни в поиске и хранится отдельно (data/resumes/_ground_truth.json) только для последующей оценки.

Скрипт evaluate.py прогоняет semantic_search для всех трёх тестовых вакансий и сравнивает выдачу с ground truth, считая:

  • Precision@K — доля кандидатов из top-K выдачи, чей истинный трек совпадает с треком вакансии;
  • MRR (Mean Reciprocal Rank) — обратная позиция первого релевантного кандидата в выдаче.

Результаты (top-5 из 12 резюме в базе)

ВакансияPrecision@5MRR
Senior MLOps Engineer1.001.00
Backend Engineer (Go)0.201.00
Data Scientist (NLP)0.601.00
Среднее0.601.00
MRR = 1.00 по всем трём вакансиям означает: самый близкий по смыслу резюме кандидат в выдаче всегда действительно релевантен вакансии — то есть основная задача (найти лучшее совпадение) решается безошибочно на тестовой базе. Precision@5 ниже (в среднем 0.60), потому что в демо-базе из 12 резюме на трек «backend_go» приходится всего ~3 кандидата — при top_k=5 система физически не может найти 5 релевантных, если их всего 3. Это ограничение размера тестовой выборки, а не ошибка алгоритма: на выборке top-3 (python evaluate.py --top-k 3) среднее Precision вырастает до 0.78.

Технический Скринер / HR-Аналитик — качественная проверка

На unit-тестах (tests/test_agents.py) проверено ожидаемое поведение обоих агентов: кандидат с полным набором требуемых навыков и стажем выше требуемого получает скор Технического Скринера >80 и пустой список рисков; кандидат без нужных навыков — скор <50 и явные риски. HR-Аналитик корректно отмечает управленческий опыт (по ключевым словам в тексте) и помечает как риск частую смену мест работы (средний тенюр <1 года). Итоговый прогон по реальной демо-базе подтверждает это на практике — пример из reports/report_Senior_MLOps_Engineer.md: кандидат с подтверждёнными Kubernetes/Docker/CI/CD/Python/Triton и стажем 13 лет получил скор Технического Скринера 100.0 и 0 рисков.

Автоматические тесты

30 unit-тестов (python -m unittest discover -s tests) — все проходят. Покрытие: подсчёт опыта по датам (5 тестов, включая открытые диапазоны "н.в." и дедупликацию пересекающихся периодов), проверка обязательных навыков (case-insensitive), агрегация semantic_search по кандидату (не по чанку), семантический дозапрос отдельного навыка внутри одного резюме (semantic_recheck_skill / query_within_resume), поведение обоих агентов на сильном/слабом резюме (включая разбивку на Плюсы/Минусы/Риски), шаг "дебатов" (явное согласие vs явное противоречие между агентами на синтетических примерах), сортировка и консистентность оркестратора, корректность рендера .md/.html отчёта.

4. Выводы

  • Прототип решает исходную проблему: ранжирование по смыслу вместо жёсткого совпадения по ключевым словам — MRR=1.00 подтверждает, что наиболее подходящий кандидат всегда оказывается первым в выдаче, даже когда формулировки в резюме и вакансии не совпадают дословно.
